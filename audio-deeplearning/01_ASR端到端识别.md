# 第 1 篇｜ASR 端到端识别：100 帧音频、5 个字答案，怎么对齐？

> 一句话核心直觉：一段话录下来是 100 帧特征，可它的文字答案可能只有 5 个字——长度对不上，而且没人告诉你"第几帧对应第几个字"。端到端 ASR 的全部智慧，就是**不要那份逐帧标注**：CTC 发明了一个"空白符"，让网络每帧随便吐，再用一套折叠规则把乱吐的序列压回那 5 个字，并对**所有能压回正确答案的吐法**一起求和当训练目标；RNN-T 再把这套改造成"能一个字一个字往外蹦"的流式版本。看懂"对齐"这两个字，就看懂了整个端到端识别。

---

## 一、先把教材那套扔一边

我们已经走了很长一段路。信号与系统系列把一段话变成了 STFT、变成了梅尔谱；深度学习基础和 3A 前端系列把卷积、门控、注意力、Conformer 这些零件都拆开讲透了。前面那条线一直在干一件事——**把声音洗干净、看清楚**。这一篇我们换个任务：把洗干净的声音**变成文字**。

传统教材（和十年前的工业系统）讲语音识别，一上来就是 HMM-GMM、三音素、决策树聚类、强制对齐。那套能用，但它有个前提特别烦人：**你得先知道每一帧音频对应哪个音素**。可现实里你手上只有一段录音和一句转写文本——"今天天气不错"六个字，录音 1.5 秒、150 帧特征。没有人告诉你第 0 到第 23 帧是"今"、第 24 到第 41 帧是"天"。要得到这份帧级对齐，传统做法要先训一个粗模型、用它去"强制对齐"、再拿对齐结果训细模型，来回迭代，又慢又绕。

端到端识别想甩掉的，正是这份"帧级对齐标注"。它的目标很干脆：

> **输入一段变长音频特征 `[B, T, F]`（T 帧、每帧 F 维），输出一串文字 `[B, U]`（U 个符号），中间不需要任何"第几帧对应第几个字"的标注。网络自己学会对齐。**

难点就卡在这句话里的一个词：**对齐**。T 通常是几十到几百帧，U 往往只有几个到几十个符号，$T \gg U$，而且这个比例每句话都不一样。网络每一帧都会算出一个"这帧像什么符号"的概率分布 `[B, T, V]`（V 是词表大小），可答案只有 U 个符号——**多出来的 T−U 个位置该填什么？连续两帧都像"今"字，算一个"今"还是两个"今"？** CTC 就是来回答这两个问题的。

翻开讲 CTC 的资料，常常一上来就甩出那个对所有路径求和的大公式，看着像天书。这一篇我们反过来：先把"对齐"这件事用一个三帧的小例子想透，公式自然就顺眼了。

## 二、CTC：发明一个"空白符"，把对齐难题变成求和

### 2.1 先看问题长什么样

假设词表只有两个真字母 `a`、`b`，一段音频编码器吐出了 3 帧，每帧给一个概率分布。我们想要的答案是 `"ab"`（2 个符号）。

网络每帧都必须吐一个符号。3 帧吐 3 个符号，怎么对出长度为 2 的 `"ab"`？最朴素的想法：规定"连续重复的合并成一个"。那么：

- `a a b` → 合并连续重复 → `a b` ✓
- `a b b` → `a b` ✓
- `a a a` → `a` ✗（没有 b）

看起来能用？但马上出事：如果答案本身就是 `"aa"`（两个连续的 a，比如"妈妈"里重复的音），那 `a a a`、`a a`、`a a a a` 全都会被合并成一个 `a`，**你永远拼不出两个连续的 a**。合并规则把"本来就该重复"的字也吃掉了。

### 2.2 空白符 ∅：一个占位又分隔的符号

CTC 的解法是往词表里塞一个额外的符号——**空白符**，记作 ∅（它不是空格，是"这一帧我没吐出新字"的意思）。于是词表从 V 个真符号变成 V+1 个（约定 ∅ 的下标是 0）。然后规定一套**折叠规则** $B$，把网络吐出的长度为 T 的原始序列（叫"对齐路径" $\pi$）压成最终文本：

> **折叠规则 $B$：第一步，合并连续重复的相同符号；第二步，删掉所有 ∅。** 顺序不能反。

有了 ∅，前面两个麻烦一起解决：

- 想要连续两个相同字（`"aa"`），就在中间塞一个 ∅ 把它们隔开：`a ∅ a` → 合并重复（三个都不相邻相同）→ `a ∅ a` → 删 ∅ → `a a` ✓。∅ 起到了**分隔符**的作用。
- 多出来的帧没字可吐，就吐 ∅ 占位：`a a ∅ b b ∅` → 合并 → `a ∅ b ∅` → 删 ∅ → `a b` ✓。∅ 起到了**占位符**的作用。

> **第一个关键认知**：空白符 ∅ 不是"静音"也不是"噪声"，它是一个**对齐工具**——它让"这一帧没有新符号产生"成为一个可以明说的选项，从而把"T 帧 → U 符号"这个长度不等的对齐问题，变成了"在每一帧的 V+1 个选项里走一条路"的问题。

### 2.3 一条路径的概率，和"所有路径求和"

现在给答案 `"ab"`、3 帧，枚举所有能折叠成 `"ab"` 的对齐路径 $\pi$（词表 `{∅, a, b}`，每帧三选一，共 $3^3=27$ 条，我们只挑合法的）：

```
路径        折叠过程                         结果
a a b   →  合并→a b, 删∅→a b               ab ✓
a b b   →  合并→a b, 删∅→a b               ab ✓
∅ a b   →  合并→∅ a b, 删∅→a b             ab ✓
a ∅ b   →  合并→a ∅ b, 删∅→a b             ab ✓
a b ∅   →  合并→a b ∅, 删∅→a b             ab ✓
```

这 5 条路径（可能还有个别等价写法，意思一样）都折叠成 `"ab"`。**它们每一条都是"正确"的对齐**——因为我们本来就不知道 a 该占第几帧、b 该占第几帧，所以凡是能压回 `"ab"` 的吐法，都该被鼓励。

一条路径的概率，是它每一帧概率的连乘（这里用了 CTC 的核心假设：**给定音频，每帧的输出互相独立**）：

$$ p(\pi \mid x) = \prod_{t=1}^{T} p(\pi_t \mid x) $$

逐项翻译：$x$ 是整段音频，$\pi_t$ 是第 $t$ 帧吐的那个符号，$p(\pi_t\mid x)$ 就是编码器在第 $t$ 帧 softmax 出来、对应 $\pi_t$ 那一格的概率。全部乘起来就是走完这条路的总概率。

那"输出文本是 `ab`"的概率，就是**所有能折叠成 `ab` 的路径概率之和**：

$$ p(y \mid x) = \sum_{\pi \in B^{-1}(y)} \prod_{t=1}^{T} p(\pi_t \mid x) $$

逐项翻译：$B^{-1}(y)$ 读作"所有能被折叠规则 $B$ 压成目标文本 $y$ 的路径的集合"（上面那 5 条就是）；对集合里每条路径算连乘概率，再全部加起来。**CTC 损失就是 $-\log p(y\mid x)$**——最大化"正确文本"的概率，等价于把那 5 条正确路径的概率一起往上推。

> **第二个关键认知**：CTC 不挑一条"最好的对齐"去训，它把**所有合法对齐一视同仁地加起来**。这正是它甩掉帧级标注的根本原因——你不用告诉它 a 在第几帧，它对所有可能的"a 在第几帧"求和，让数据自己把概率质量堆到对的地方。

### 2.4 别真去枚举：前向-后向把指数变线性

你可能已经慌了：路径数随 T 指数爆炸，27 条还能枚举，300 帧呢？CTC 真正能训，靠的是一个**动态规划**（和 HMM 的前向-后向同源）：定义 $\alpha_t(s)$ 为"到第 $t$ 帧、刚好对齐到目标序列第 $s$ 个位置"的所有路径概率和，它只依赖 $\alpha_{t-1}$ 的相邻几格，于是 $O(T\cdot U)$ 就能把那个指数级求和算出来。这块推导我们不展开——你只要知道**那个"对所有路径求和"不是靠枚举、是靠递推**，心里就不虚了。好消息是：PyTorch 的 `torch.nn.CTCLoss` 把这套全包了，你喂 logits 和长度就行。

### 2.5 CTC 的软肋：每帧独立

回头看 2.3 那个连乘公式——它假设**每帧输出独立**。这意味着 CTC 不建模"吐了 a 之后下一个更可能是 b"这种输出符号之间的依赖。它靠编码器把上下文都塞进每帧特征里来间接补偿，但本质上**没有语言模型**。实践里 CTC 解码常要外挂一个语言模型来救。这个软肋，正是 RNN-T 要补的。

## 三、RNN-T：把 CTC 改成能"一个字一个字往外蹦"

### 3.1 为什么需要它

CTC 有两个不痛快：一是刚说的**每帧独立、不建模输出依赖**；二是它的解码天然是"看完整段再折叠"，**不好做严格流式**（虽然有流式变体，但别扭）。而输入法、实时字幕、会议转写这些场景，要求**边说边出字**。RNN-T（RNN-Transducer）就是冲着这两点来的。

### 3.2 三件套

RNN-T 把网络拆成三块：

```
音频特征 [B,T,F] ──► Encoder（声学）─────► f_t   [B,T,D]
                                                    │
已吐出的字 [B,U] ──► Prediction Net（像语言模型）─► g_u [B,U,D]
                                                    │
                         Joint Net（f_t 和 g_u 捏一起）
                                   │
                         logits [B, T, U, V+1]
```

逐块翻译：
- **Encoder**：和 CTC 的编码器一样，吃音频吐帧级特征 $f_t$。可以直接复用我们学过的 Conformer。
- **Prediction Network**：吃**已经吐出来的字**，预测"下一个字的语境"$g_u$。它就是个语言模型——这就补上了 CTC 缺的"输出符号之间的依赖"。注意它只看文字、不看音频。
- **Joint Network**：把某一音频帧 $f_t$ 和某一文字位置 $g_u$ 捏一起（通常相加后过一个小前馈），输出在这个 $(t,u)$ 格点上、下一个符号是谁的概率分布，维度 `[B,T,U,V+1]`。

### 3.3 格点上的两种走法：吐字 vs 前进一帧

RNN-T 的解码想象成在一张 $T\times U$ 的网格上从左下角走到右上角。站在格点 $(t,u)$（已经处理到第 $t$ 帧、已经吐了 $u$ 个字），有两种动作：

- **吐一个真字**：$u \to u+1$，往上走一格，当前帧 $t$ 不变（同一帧可以连吐好几个字）。
- **吐空白符 ∅**：$t \to t+1$，往右走一格，表示"这帧没新字了，推进到下一帧音频"。

> **把它想成打字**：按一个字母键 = 吐一个真字（光标右移、音频不动）；按空格/回车 = 吐 ∅（翻到下一帧音频）。一段音频听下来，就是这两种按键交替，走出一条从头到尾的路径。

和 CTC 一样，RNN-T 损失也是**对所有能走到终点、吐出正确文本的路径求和**，同样用动态规划算（PyTorch 这块一般用 `torchaudio.functional.rnnt_loss` 或 warp-transducer）。差别在于：每一步的概率现在**依赖已经吐出的字**（因为 Prediction Net 在），所以它建模了输出依赖；而且解码天然是"来一帧、吐若干字、再来一帧"，**严格流式、因果**。

> **第三个关键认知**：CTC 和 RNN-T 都在"对所有合法对齐求和"这件事上同源，区别是 RNN-T 多了一条**看着已吐文字说话**的 Prediction 支路，于是它既建模了语言依赖，又能一帧一帧地流式吐字。代价是那张 `[B,T,U,V]` 的四维联合张量很吃显存。

## 四、第三条路：AED / Whisper 用注意力直接学软对齐

还有一类端到端 ASR 根本不用 ∅，叫**注意力编解码**（AED，代表作 LAS、Whisper）。它借用翻译那套 encoder-decoder：编码器把音频编成 `[B,T,D]`，解码器**自回归**地一个字一个字生成，每生成一个字就用**交叉注意力**回头去音频序列里"看"该参考哪些帧——对齐不再靠 ∅ 折叠，而是**注意力权重自己学出来的软对齐**（第 $u$ 个字在哪些帧上权重高，就是它对齐到哪）。

AED 的好处是解码器自带强语言建模、音质上限高（Whisper 就是这路线、海量数据硬怼）；坏处是**自回归、非流式**（要等编码器看完整段），且注意力对齐在长音频/静音段容易"跑飞"（漏读、重复、早停）。

三方对比：

| | 怎么对齐 | 建模输出依赖 | 能否严格流式 | 典型场景 |
|---|---|---|---|---|
| **CTC** | ∅ + 折叠，对所有路径求和 | 否（每帧独立） | 勉强（变体） | 强制对齐、配语言模型、轻量识别 |
| **RNN-T** | ∅ 格点，对所有路径求和 | 是（Prediction Net） | **天然流式** | 输入法、实时字幕、端侧/会议 |
| **AED** | 交叉注意力软对齐 | 是（自回归解码器） | 否（非流式） | 离线高精度、Whisper 这类大模型 |

## 五、代码实战：跑一次 CTC loss + 贪心解码

下面这段在 CPU 上就能跑通。我们搭一个极小的"编码器"（Conv 下采样 + 双向 GRU），输出 logits `[B,T,V]`，然后用真实的 `torch.nn.CTCLoss` 算损失，再写贪心解码（argmax → 折叠）把它变回文本。词表约定 `0=∅`。

```python
import torch
import torch.nn as nn
import torch.nn.functional as F

torch.manual_seed(0)

B, F_in, V = 2, 40, 6        # 批大小 2, 输入每帧 40 维, 词表 6（含 ∅=0, 真符号 1..5）
BLANK = 0

class TinyEncoder(nn.Module):
    """Conv 时间下采样 + 双向 GRU，吐帧级 logits。"""
    def __init__(self, f_in, v, d=64):
        super().__init__()
        # Conv1d 在时间轴上 stride=2 下采样一次（ASR 常见：降帧率省算力）
        self.conv = nn.Conv1d(f_in, d, kernel_size=3, stride=2, padding=1)
        self.gru  = nn.GRU(d, d, batch_first=True, bidirectional=True)
        self.proj = nn.Linear(2 * d, v)   # 双向→2d，投到词表

    def forward(self, x):                 # x: [B, T, F_in]
        x = x.transpose(1, 2)             # -> [B, F_in, T]  (conv1d 要求通道在中间)
        x = F.relu(self.conv(x))          # -> [B, d, T']    T'≈T/2
        x = x.transpose(1, 2)             # -> [B, T', d]
        x, _ = self.gru(x)                # -> [B, T', 2d]
        return self.proj(x)               # -> [B, T', V]

enc = TinyEncoder(F_in, V)

# 造一段假音频特征：T=50 帧
T_in = 50
x = torch.randn(B, T_in, F_in)
logits = enc(x)                           # [B, T', V]，T'=ceil(50/2)=25
print("logits:", logits.shape)            # torch.Size([2, 25, 6])

# ---- CTC loss ----
# CTCLoss 要求输入 [T, B, V] 的 log 概率，且在类别维做 log_softmax
log_probs = logits.log_softmax(dim=-1).transpose(0, 1)   # [T', B, V]
print("log_probs:", log_probs.shape)      # torch.Size([25, 2, 6])

# 两条目标文本（用 1..5 的真符号，不含 ∅）：比如 [3,1,4] 和 [2,5]
targets = torch.tensor([3, 1, 4, 2, 5])   # 拼平放一起
target_lengths = torch.tensor([3, 2])     # 第 1 句 3 个字, 第 2 句 2 个字
input_lengths  = torch.full((B,), log_probs.size(0), dtype=torch.long)  # 每句 25 帧

ctc = nn.CTCLoss(blank=BLANK, zero_infinity=True)
loss = ctc(log_probs, targets, input_lengths, target_lengths)
print("CTC loss:", loss.item())           # 一个标量，初始随机权重下 loss 较大

# ---- 贪心解码：argmax 每帧 → 折叠（合并重复 + 删 ∅）----
def ctc_greedy_decode(logits_bt_v, blank=BLANK):
    best = logits_bt_v.argmax(dim=-1)      # [B, T']，每帧取最可能符号
    results = []
    for seq in best:                       # 逐句折叠
        out, prev = [], None
        for s in seq.tolist():
            if s != prev and s != blank:   # 跳过重复, 跳过 ∅
                out.append(s)
            prev = s
        results.append(out)
    return results

print("greedy:", ctc_greedy_decode(logits))   # 两句解码出的符号列表（随机权重下是乱的）
```

跑完你会看到：`logits` 是 `[2,25,6]`——50 帧被 conv 下采样成 25 帧；`log_probs` 转成了 CTCLoss 要的 `[25,2,6]`；loss 是个标量。贪心解码把每帧 argmax 后按折叠规则压回符号列表。真实训练里把 loss 反传、迭代，网络就会慢慢把概率质量堆到正确路径上。注意几个工程坑都在代码里了：**blank 下标要和 CTCLoss 的 `blank` 参数一致**、**log_softmax 不能忘**、**输入要转成 `[T,B,V]`**、**input_lengths 要用下采样后的 T'**（不是原始 50，这是新手最常踩的 off-by 错）。

RNN-T 的 joint 这里就不整段跑了，核心只有一句：encoder 的 `[B,T,D]` 和 prediction 的 `[B,U,D]` 要**广播成 `[B,T,U,D]`** 再过 joint，输出 `[B,T,U,V+1]`——那个凭空多出来的 `T×U` 维度就是它吃显存的根源，端侧要靠限制 U 的搜索宽度来压。

## 六、这在工程里解决什么问题

| 场景 | 选哪个 | 为什么 |
|---|---|---|
| 手机输入法 / 实时字幕 / 会议转写 | **RNN-T** | 严格流式、低延迟、自带语言建模，端侧主力 |
| 离线转写、字幕生成、追求最高精度 | **AED（Whisper 类）** | 可看全局、语言能力强，不在乎实时性 |
| 强制对齐（给音频打时间戳、做数据标注） | **CTC** | 对齐路径本身就是副产品，拿来标帧级边界 |
| 唤醒后短指令识别、超轻量端侧 | **CTC**（+ 小语言模型） | 结构最简、算力最省 |

几个一线视角：
- **指标是 WER（词错误率）**，由替换+删除+插入错误除以总词数算。但 WER 和"听起来对不对"也会背离——漏一个"不"字，WER 只掉一点，语义全反了。
- **流式延迟**：RNN-T 要控制"向前看多少帧"（look-ahead），看得越多精度越高但延迟越大，这是端侧调参的核心权衡——本质还是那条**不能看太多未来帧**的实时因果红线。
- **下采样省算力**：代码里 conv stride=2 把帧率砍半，是 ASR 编码器的标配——语音没必要每 10ms 都出一个结果，降帧率直接省一半后续计算。
- **显存**：RNN-T 的 `[B,T,U,V]` 联合张量在长音频+大词表下非常吃显存，训练常要切块或用显存优化版 loss。

---

## 七、埋一个钩子

这一篇我们走通了"音频 → 文字"：核心是**对齐**，CTC 用空白符把它变成对所有路径求和，RNN-T 再把它改成流式吐字。那反过来呢——给你一句文字，怎么**生成一段自然的语音**？"文字 → 音频"同样面临长度对不齐的难题（几个字要撑开成几百帧波形），但解法完全不同。下一篇进入 **TTS 语音合成**。

---

## 本篇小结

- **核心难点**：端到端 ASR 要把变长音频 `[B,T,F]` 变成短得多的文本 `[B,U]`，且不要帧级对齐标注。一切围绕"对齐"展开。
- **CTC**：引入空白符 ∅ + 折叠规则（合并重复→删 ∅），把对齐变成"在每帧 V+1 个选项里走一条路"，损失 = 对**所有能折叠成目标的路径**概率求和，用前向-后向动态规划算（`torch.nn.CTCLoss`）。软肋是每帧独立、不建模输出依赖。
- **RNN-T**：encoder + prediction（语言模型支路）+ joint 三件套，在 $T\times U$ 格点上"吐字 / 前进一帧"两种走法，补上了输出依赖、且天然流式；代价是 `[B,T,U,V]` 四维张量吃显存。
- **AED/Whisper**：用交叉注意力学软对齐、自回归解码，精度上限高但非流式。
- **工程意义**：RNN-T 是端侧/实时识别主力，AED 是离线高精度主力，CTC 擅长强制对齐与超轻量场景；注意 blank 下标一致、log_softmax、`[T,B,V]`、下采样后的 input_lengths 这几个必踩的坑。
- **下一步**：把方向反过来，看"文字 → 音频"的 TTS 怎么解决另一侧的长度对齐难题。
